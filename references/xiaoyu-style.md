# 蒸馏小余 2.0 写作风格

这是“蒸馏小余”公众号文章的默认写作规范。目标不是模仿固定口头禅，而是把 AI Agent、AI 编程和工程知识库内容改成更成熟、更清楚、更适合公众号阅读的技术文章。

## 核心定位

蒸馏小余：把 AI Agent、AI 编程和工程知识库的前沿内容，蒸馏成开发者能直接用的工作流。

默认写作目标：

- 更容易读
- 更像成熟编辑改过的文章
- 信息推进更顺
- 保留技术准确性
- 保留通俗解释能力
- 去掉模板腔、口头禅和过度提示感
- 标题先抓住读者体感问题，再承载技术名词

## 蒸馏小余 2.0 规则

1. 先下判断，不先说感受。少用“我觉得”“我认为”“我看到后发现”。
2. “一句话总结”一篇最多出现 1 次，只能放在开头。
3. 少用“这件事、这个点、这一层、这个问题”，多用具体名词。
4. 每一段只推进一个信息点，不要一段里同时下结论、举例、抒情、重复总结。
5. 短句负责提速，长句负责解释，不要整段都是碎短句。
6. 少用“真正、核心、本质、最重要”这种提示词反复抬重点。
7. 每个判断后面，必须立刻跟原因、例子或解释。
8. 小标题尽量写成读者会关心的问题，或者写成清楚的判断句。
9. 结尾给行动建议，不写空泛感慨。
10. 删除不带信息增量的口头过渡句，尤其是作者习惯性抬重点的话。

## 标题规范

技术公众号标题的任务不是展示文章懂多少概念，而是让目标读者在推荐流里立刻知道：这篇文章能解释一个自己遇到过的问题。

默认标题策略：

1. 先写读者体感，再放技术名词。优先使用“慢、贵、卡住、忘事、幻觉、不可控、交付烂尾、成本压不住、首 token 等太久”等开发者能感知的问题。
2. 技术名词放在解释路径里，不要单独当入口。`Prompt Caching 为什么是 Agent 的地基？` 弱于 `Agent 为什么越跑越贵？先看 Prompt Caching`，但不要把所有标题都写成“为什么”。
3. 先判断文章最强的标题机制：痛点诊断、误区纠正、方法替换、结果前置、边界提醒、清单交付、能力变化。句式跟机制走，不跟固定模板走。
4. 标题必须包含一个清楚承诺：解释原因、给出判断、提供清单、拆解路径、复盘实测结果，至少命中一种。
5. 长度优先控制在 18-32 个中文字符；复杂技术题可以放宽到 36 个字，但前 18 个字必须出现核心痛点、强判断或明确收益。
6. 不为点击牺牲准确性。标题可以制造悬念，但正文必须兑现标题承诺，不能把“可能、局部、取决于场景”写成绝对结论。
7. 不默认使用 `为什么...？...` 或 `X 为什么 Y？从 A 到 B...`。问句只在文章确实围绕一个读者正在问的问题展开时使用；5 个候选标题里最多 1 个使用“为什么”。

优先使用这些标题结构：

- 动作提醒 + 方法：`别再给 RAG 硬塞 chunk：SAG 用「事项+实体」接证据链`
- 误区纠正 + 判断：`RAG 不缺更多 chunk，缺一条证据链`
- 方法替换 + 技术对象：`把 chunk 变成证据链：SAG 的轻量多跳做法`
- 结果前置 + 原因排除：`Recall@2 提升 11 个点，SAG 靠的不是更大向量模型`
- 工程入口 + 使用收益：`一份 MCP 配置，把项目文档变成 Agent 工具箱`
- 误区纠正 + 正确判断：`长上下文不是免费记忆：真正贵的是 KV Cache`
- 工程后果 + 解决对象：`Agent 越跑越贵，先看 Prompt Caching`
- 实测发现 + 可复用结论：`我用 Claude Code 跑完一个需求，发现 HTML 比 Markdown 更适合交付`
- 最大坑不在 A，而在 B：`Agent 交付烂尾，问题不在工具多，而在上下文乱`
- 新能力到底改了什么：`Claude 新功能真正改变的，不是写代码，而是少盯着交付`
- 体感问题 + 技术路径：`为什么大模型第一个字总是最慢？从 Prefill 到 KV Cache 讲清楚`

标题自检：

- 读者不懂技术名词时，是否仍然知道为什么要点开？
- 标题是否对应一个真实工作流后果，而不是只在解释概念？
- 是否有“痛点 -> 方法 / 误区 -> 判断 / 结果 -> 原因 / 不是 A 而是 B / 问题 -> 路径”这类明确推进关系？
- 如果标题是问句，是否真的比判断句、提醒句、结果句更准？
- 是否避免了空泛词：深度解读、全面解析、一文读懂、重磅、炸裂、颠覆、史诗级？
- 第一屏 200 字内是否兑现标题承诺，而不是先铺背景？

每篇文章成稿前必须生成 5 个标题候选：

1. 推荐标题：最适合推荐流，痛点明确，技术路径清楚。
2. 稳妥标题：更准确克制，适合老读者。
3. 大众标题：减少术语，扩大入口。
4. 专家标题：保留关键技术名词，适合垂直人群。
5. 反差标题：用“不是 A，而是 B”或“最大坑不在 A”制造判断感。

这 5 个候选必须至少覆盖 4 种句式；如果都长得像“为什么？从 A 到 B”，必须重写。

最终选择时，优先选“推荐标题”。除非技术准确性不足，才退回“稳妥标题”。

## 硬约束

- 尽量删掉或替换这些句式：
  - 我觉得最有价值的地方
  - 如果只用一句话总结
  - 很多人会以为
  - 真正关键的地方
  - 这件事真正提醒我们的是
- 如果必须保留这类句式，每类最多出现 1 次。
- 连续短句不要超过 3 句。
- 每个小节都要有具体名词，不能一直用“这件事”代指。
- 不要为了顺口增加空洞句子。
- 不要改变原文事实、数字、引用关系和作者原意。
- 原文里不确定的内容，不要硬编，可以保留为谨慎表达。
- 如果原文有代码，保留必要代码，并把注释改得更易懂。
- 如果原文适合列表，就保留列表；如果原文列表过碎，就改成更自然的段落。
- 禁止只有概念名词的标题，例如“Prompt Caching 详解”“某某论文解读”“某某框架深度分析”。
- 禁止标题承诺超过证据边界，例如把单个案例写成行业定论。

## 文章结构

优先使用下面的结构，但不要机械套模板：

1. 先确定标题承诺，再写正文；标题承诺决定第一屏和文章结构。
2. 开头 200-300 字内给出场景、判断、读者收益，并兑现标题里的痛点。
3. 中段拆成 3-5 个清楚判断，每个判断后跟原因、例子或边界。
4. 给一个可复用对象：清单、表格、Prompt、工作流、决策标准或模板。
5. 加入作者判断：适合谁、不适合谁、我会怎么用、最大坑在哪里。
6. 结尾给具体行动建议和匹配文章资产的 CTA。

## 语言控制

适合：

- 具体名词
- 清楚判断
- 场景化解释
- 方法和边界一起写
- “判断 -> 原因 -> 方法 -> 边界”的推进链条

不适合：

- 学术论文式表述
- 过度抽象的架构黑话
- 只堆 API 名词，不解释工作流后果
- 连续碎短句堆节奏
- 反复用“真正关键”“本质上”“如果只用一句话总结”抬重点

## 修订检查

成稿后必须做一次自检：

- 开头是不是一上来就在讲观点，而不是讲作者感受。
- 标题是不是先抓读者体感、工程后果或可验证结果，再承载技术名词。
- 是否至少生成过 5 个标题候选，并且至少覆盖 4 种句式。
- 是否避免把“为什么”当成默认标题模板。
- 第一屏是不是兑现了标题承诺。
- 文中“我觉得 / 一句话总结 / 真正关键”是不是明显变少。
- 有没有连续很多个碎短句，读起来像口播稿。
- 有没有太多“这件事 / 这个点”而缺少具体对象。
- 每个小节是不是都在推进信息，而不是反复强调重点。
- 每个判断后面是否有原因、例子或解释。
- 结尾是不是给了动作建议，而不是停在价值判断。
