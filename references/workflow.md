# 公众号文章生成流程总结

这是目前已经跑通、并且经过多轮修正后的实际流程。

## 一句话版本

稳定流程不是：

`写 Markdown -> 打开 Doocs 网站 -> 点复制 -> 粘到公众号`

而是：

`整理素材 -> 网络补强 -> 写 Markdown -> 生成配图和封面 -> 本地 Doocs 渲染 -> WeChat API 发草稿`

## 标准流程

### 1. 获取素材

来源可以是：

- X 链接
- GitHub 仓库
- 网页文章
- 访谈笔记
- 用户给出的现成 markdown

关键点：

- 素材必须落本地
- 保留原链接和来源信息
- 对 repo / docs 类内容，要先做结构化理解，再写文章

### 1.5 用网络搜索补强素材库

这一阶段应该默认启用。

很多文章如果只依赖原始素材，最后最多只能写成“改写版摘要”，还不够支撑成完整公众号文章。真正让文章质量上来的，往往是这一步补进去的高质量背景信息。

推荐补充的内容：

- 官方文档
- 仓库 README / CHANGELOG / release notes
- 作者或维护者的说明
- 高质量技术博客
- 真实案例或落地场景
- 与其他方案的对比

这一步的目标不是“搜一堆链接”，而是补齐文章真正缺的东西：

- 为什么重要
- 解决了什么问题
- 和其他方案有什么差异
- 有没有可信事实和例子可用

建议做法：

1. 先根据原始素材列出 3 到 5 个待补问题
2. 再做有目标的搜索
3. 只保留高质量结果
4. 把有价值的信息折回文章主线

信息质量优先级：

1. 官方和一手材料
2. 作者 / 维护者直接表达
3. 高质量技术分析
4. 普通聚合转载

如果内容涉及会变化的事实，比如版本、价格、star 数、发布时间、API 行为，就必须在写作前重新确认。

### 2. 写中文文章

写作风格默认是 `码农小余`，重点是：

- 先讲结论
- 再拆结构
- 语言直白，不堆术语
- 技术细节要对，但表达要更容易读

文章 frontmatter 至少要有：

- `title`
- `source`
- `source_author`
- `written_style`
- `created_at`
- `coverImage`
- `summary`

### 3. 生成正文配图

配图流程已经被证明需要“先写 prompt 文件，再出图”。

最稳做法：

1. 先写 `illustrations/<slug>/outline.md`
2. 再写 `prompts/*.md`
3. 再逐张生成
4. 插回正文 markdown

原因很简单：

- prompt 文件可复用
- 出错后方便局部重跑
- 图风可以持续统一

### 4. 生成封面图

封面图目前的默认规范：

- 主比例 `2.35:1`
- 必须兼容居中 `1:1` 裁剪

这条规则来自公众号实际展示场景：

- 头图更适合宽横幅
- 列表 / 缩略图又常常接近方形裁切

所以封面 prompt 必须明确要求：

- 标题放中间
- 主视觉放中间
- 关键信息不要贴边

### 5. 本地 Doocs 渲染

这一步现在默认必须走本地，不优先走网站。

原因：

- 在线 Doocs 页面不稳定
- 复制按钮容易失效
- 剪贴板权限会失败
- 页面 DOM 变化会把自动化打断

本地渲染的目标不是“复刻网站操作”，而是“得到可投递到公众号 API 的 HTML”。

### 6. 发布前兼容处理

这是最容易被忽略、但最关键的一步。

公众号不会老老实实保留你的全部 CSS，所以发布前要补一层兼容内联化。

目前这层主要负责：

- 保留 body 级样式
- 给段落、标题、表格、引用、代码块补内联样式
- 处理正文图片占位和上传
- 清洗列表 marker 问题

### 7. API 发草稿

最后一步才是发公众号。

推荐参数：

- `--cover`
- `--summary`
- `--author`

不要依赖“自动推断封面”，因为那会让结果越来越不稳定。

## 当前已验证有效的策略

### 渲染策略

- 本地 Doocs 渲染优先
- 在线 Doocs 只兜底

### 封面策略

- `2.35:1`
- `1:1` 安全裁剪区

### 列表策略

- `ul` 和 `ol` 必须保留原生 marker
- `li` 必须是 `display: list-item`
- 如果 `li` 文本本身带 `•`，发布前必须清洗，避免双黑点

### 代码块策略

- GitHub Dark 风格
- 尽量在发布前内联关键样式

## 为什么这套流程适合做成 skill

因为它不是一篇文章的手工操作记录，而是一条已经反复验证过的生产链路：

- 有固定输入
- 有固定中间产物
- 有固定错误模式
- 有明确的默认值和 fallback

这正适合 skillhub 分发。
